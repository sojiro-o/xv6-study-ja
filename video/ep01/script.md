## 1. 導入：printfはどうやって画面に文字を出してるの？

C言語を書いたことがある人なら、画面に文字を出す printf を使ったことがあるよね。 [画面: 1行のコード printf("hi\n"); を表示]
でも、「printf ってどうやって画面に文字を出してるの？」と考えたことはあるかな。
教育用の小さな OS である xv6 で printf のコードを覗いても、画面に電気信号を送る処理はどこにもないんだ。 [画面: アプリの printf → × → ディスプレイ（直接は届かない）]
printf は文字を1つずつ整えて、write という関数を呼んでいるだけなんだよ。
そしてその write でも、アプリ自身は画面の装置に直接触れていないんだ。
実はアプリは途中で OS の本体、カーネルにバトンを渡し、代わりに文字を出してもらっているんだよ。 [画面: 上段＝ユーザーモード（アプリ）、中段＝スーパーバイザーモード（カーネル）、下段＝ハードウェア]
こんにちは、耳で楽しむ OS のしくみラジオへようこそ。
今日持ち帰ってほしい中心の仕組みは、たった一つだけだよ。
それは、「アプリは OS に、決まった入口からお願いする」という仕組み、システムコールなんだ。 [画面: 境界線にある唯一の入口「システムコール」を強調]
耳だけで追えるよう順番に話していくから、移動中や作業のお供に気楽に聞いてね。

## 2. もしアプリが何でも自由に触れたら？

まずは、「どうしてわざわざ OS にお願いするの？」という疑問から考えよう。 [画面: セクション見出し「なぜ境界線が必要なのか」]
アプリが直接画面やディスクを触れたほうが、手っ取り早そうに思えるよね。
でも、すべてのアプリが装置やメモリを自由に触れたら、すぐに3つの事故が起きるんだ。 [画面: 仕切りがない状態で複数アプリが装置・メモリへ直接伸びる図]
1つ目は、うっかりミスで全体が壊れることだよ。
番地の計算を1つ間違えただけで、大事なファイルを消したり OS を壊して全体を止めてしまうんだ。 [画面: 問題① ミスでファイルやOSメモリを破壊]
2つ目は、他のアプリの情報を盗み見られることだよ。
別のプログラムが持つデータを、無関係なアプリが勝手に読み取れてしまうよね。 [画面: 問題② 他アプリのメモリを覗き見]
3つ目は、装置の取り合いで出力が混ざることなんだ。
2つのアプリが同時に画面やディスクへ命令を送ると、文字やデータが混ざって壊れてしまうよ。 [画面: 問題③ 同時アクセスで出力が混ざる]
だから OS は、アプリには自分の持ち分のメモリだけを触らせて、危険な操作はカーネルに閉じ込めているんだ。 [画面: アプリを上段に隔離する仕切り線]
そのうえで、安全にお願いするための決まった入口として、システムコールを用意しているんだよ。

## 3. 役所の窓口のイメージと、実際のCPUとの3つの違い

システムコールの動きは、「ガラスの仕切りがある役所の窓口」にたとえるとわかりやすいよ。 [画面: ロビー（アプリ）と事務室（カーネル）を隔てる窓口]
ロビーにいるアプリは、仕切りに阻まれて奥の事務室へ勝手に入ることはできないんだ。
頼みたいときは、窓口のトレイに「手続き番号」と「必要な情報」を置いて呼び鈴を鳴らすよ。 [画面: トレイに「番号：16」「出力先・文字・文字数」を置いて呼び鈴]
すると事務室のカーネルが受付に出てきて、中身を確かめてから安全に作業してくれるんだ。
終わったら「2文字書けたよ」という結果をトレイに置いて返してくれるんだよ。
ただ、この窓口のたとえは、実際の RISC-V 版 xv6 と大きく違う点が3つあるんだ。 [画面: 「窓口の比喩と実際の違い 3つ」]
1つ目は、アプリとカーネルという2人の人間が向かい合っているわけではないことだよ。
実際にはたった1つの CPU コアが、権限スイッチを切り替えてカーネルの命令を動かし始めるんだ。 [画面: 1つのCPUが「アプリの帽子」から「カーネルの帽子」へかぶり直す]
1人の作業員が帽子をかぶり直して、自分で事務室側へ回る動きに近いんだよ。
2つ目は、トレイが紙ではなく、CPU 内部にある「レジスタ」という少数の置き場所だということなんだ。
レジスタは1組しかないから、カーネルが動く前にアプリの値をメモリへ丸ごと退避する必要があるよ。 [画面: CPU内の1組のレジスタ → メモリの退避シートへ保存]
3つ目は、ロビーから事務室がガラス越しに見えているわけではないことだよ。
xv6 では、アプリごとに見えるメモリの地図、ページテーブルがカーネルと別になっているんだ。 [画面: アプリ用のメモリ地図（カーネル領域は記載なし・通行禁止）]
カーネルの番地は地図にないか通行禁止だから、触れた瞬間に CPU がエラーで止めてくれるんだよ。

## 4. レジスタとecallで境界を越える往復の旅

それじゃあ比喩を離れて、xv6 で write を呼んで2文字出すときの往復の旅を追ってみよう。 [画面: セクション見出し「システムコール往復の流れ」]
RISC-V の CPU には権限モードがあり、xv6 は普段2つのモードを切り替えて使うよ。
アプリが動く制限付きの「ユーザーモード」と、カーネルが動く特権付きの「スーパーバイザーモード」だね。 [画面: 上段＝ユーザーモード、下段＝スーパーバイザーモード]
アプリは勝手にモードを変えられないから、正当にカーネルを呼ぶ手段は専用命令の ecall だけなんだ。 [画面: 唯一の正当な入口「ecall 命令」]
write を呼ぶとき、アプリは a0 から始まるレジスタに、出力先や文字数などの引数を最大6個入れるよ。
そしてアプリ側の小さな入口は、a7 レジスタに write の番号 16 を入れて ecall を実行するだけなんだ。 [画面: a7に番号16を入れ ecall を実行]
ecall が実行されると、CPU の回路は瞬時に4つのことを行うよ。
権限をスーパーバイザーモードへ引き上げ、いま実行した ecall の番地を記録するんだ。
同時に、割り込みなど他の用事と見分ける理由番号 8 を記録し、決まった受付番地へジャンプするよ。 [画面: ecallの4動作（①特権昇格 ②番地記録 ③理由8番 ④受付へジャンプ）]
ただし CPU が自動でやるのはここまでで、メモリの地図もレジスタもまだアプリ用のままなんだ。
もし普通の場所で地図をカーネル用に切り替えたら、実行中の命令自身の番地が消えて暴走してしまうよね。
そこで活躍するのが、メモリ1区画、つまり1ページ分の「トランポリン」という飛び込み台なんだ。 [画面: 両方の地図の最高番地に共通配置された「トランポリン」]
この領域だけはアプリ用とカーネル用の両方の地図で同じ一番上の番地にあるから、足場が消えないんだよ。
ここでアプリのレジスタ一式を退避シートに保存し、地図を切り替えて C言語の usertrap 関数へ飛ぶんだ。
usertrap は理由番号が 8、つまりシステムコールだと確かめると、戻り先の番地に 4 バイトを足すよ。 [画面: usertrap 内で戻り先番地に +4 バイト]
ecall 命令1つ分の長さが、ちょうど 4 バイトだからなんだ。
ここで予想してみてほしいんだけど、もしこの「4バイト進める処理」を忘れたまま帰ったら何が起きると思う？ [画面: 問いかけ①「戻り先に +4 し忘れたらどうなる？」]
ちょっと想像してみてね。
正解は、「同じシステムコールを無限に繰り返して、先に進めなくなる」なんだ！
記録されていたのは ecall 自身の番地だから、戻った瞬間にまた同じ ecall を実行してしまうんだよ。 [画面: ecall へ戻って再び飛び込む無限ループ]
戻り先を進めたら、司令塔である syscall 関数が呼ばれるよ。
syscall 関数は退避シートの a7 から番号を取り出し、関数の一覧表から write の本体を呼ぶんだ。 [画面: syscall関数：a7の番号(16)から処理関数を実行]
未登録の番号ならマイナス1を返し、無事に書けたら文字数の 2 を退避シートの a0 に書き込むよ。
帰りは再びトランポリンで地図をアプリ用に戻し、退避シートからレジスタを復元するんだ。
すると a0 に結果の 2 が入った状態でユーザーモードへ戻り、ecall の次の命令から再開するよ。 [画面: a0 に戻り値 2 を持ってアプリの次の命令へ復帰]

## 5. echoの改造実験と、消えたexitの謎

教材の第1章では、この動きを確かめるため syscall 関数へ5行だけ表示コードを足す実験をしているよ。 [画面: セクション見出し「5行の改造でシステムコールを観察する」]
足す場所は、番号に対応する処理関数を呼び出した「すぐ後ろ」なんだ。
すべてのプログラムで出すと、コマンドを受け付けるシェルだけで画面が埋まるよ。
だから実行中のプログラム、つまりプロセス名が echo のときだけ名前と戻り値を表示するんだ。 [画面: syscall関数の呼び出し直後に「echoなら表示」を追加]
echo は渡された文字を画面に出すコマンドだよ。
英語の挨拶である2文字の hi を渡すと、write で2文字、もう一度 write で改行を書いて、最後に終了の exit を呼ぶんだ。 [画面: echo の処理順：write("hi") → write(改行) → exit(0)]
実際に動かすと、最初に中身を入れ替える exec、次に2文字の write、改行1文字の write、の3行が出るよ。 [画面: 実行ログの3行（exec -> 2、write -> 2、write -> 1）]
最初に exec が出るのは、シェルが分身のプロセスを echo に入れ替える途中で名前が echo に変わって戻るからなんだ。
ところがね、ここで2つ目の予想タイムだよ！
echo は最後で間違いなく exit を呼んでいるのに、exit の記録は1行も出てこないんだ。 [画面: 問いかけ②「最後に呼んだ exit が表示されないのはなぜ？」]
バグではなく仕組み通りの動きなんだけど、どうして exit だけ表示されないんだと思う？
ヒントは、表示コードを「処理関数を呼んだすぐ後ろ」に置いたことだよ。
ちょっと考えてみてね。
正解は、「exit の処理に入ると、二度と syscall 関数の次の行へ戻ってこないから」なんだ！ [画面: exit はプロセスを終了し別プロセスへCPUを譲るため戻らない]
write や exec は仕事が終われば syscall 関数へ帰ってくるから、後ろの表示コードが動くよね。
でも exit はプロセス自身を終了させて別のプロセスへ CPU を譲るから、後ろの行には永遠に戻ってこないんだよ。

## 6. まとめと、PCに戻ったら試せる小さな実験

それじゃあ、今日のお話を最後にまとめよう。 [画面: まとめカード「システムコールの要点」]
アプリの printf や write は、直接装置を触れないユーザーモードで動いているんだったね。
仕事を頼むときは、a0 からのレジスタに引数、a7 に番号を入れて、唯一の窓口 ecall でカーネルを呼ぶよ。
カーネルはトランポリンでレジスタ退避と地図切り替えを行い、usertrap と syscall で仕事をして結果を a0 に返すんだ。 [画面: 対応表（入口＝ecall、番号＝a7、戻り値＝a0、司令塔＝usertrap / syscall）]
つまりシステムコールは、「アプリが OS に、決まった入口から安全にお願いする仕組み」なんだよ。
いま耳だけで聞いている人も、あとで PC に戻ったらぜひ手元で動かしてみてね。
リポジトリ直下で scripts の check-lab に syscall-trace を渡すだけで、改造から echo の確認、片付けまで自動で試せるよ。 [画面: ./scripts/check-lab syscall-trace]
正確なコマンドと、自分で改造したり exit も表示させる課題がある第1章・第5節へのリンクは概要欄に置いておくね。
最後まで聞いてくれてありがとう、また次の回も耳から一緒に OS を探検しようね！
