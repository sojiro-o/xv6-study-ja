## 3. メインコーナー：システムコールの往復と帰り道の秘密

<!-- SE: ページをめくる音 -->
まずは「どうしてアプリがわざわざ OS に頼みごとをするのか」から考えよう。 [画面: メインコーナー「なぜアプリは直接触れないのか」]
もしアプリが画面やディスクやメモリを直接触れたら、すぐに3つの事故が起きるんだ。
1つ目は、番地の計算ミス1つで大事なファイルや OS を壊して止めてしまうことだよ。 [画面: 困りごと① ミスでファイルやOSを破壊]
2つ目は、他のアプリが持つデータを無関係なアプリに盗み見られてしまうことだね。 [画面: 困りごと② 他アプリのメモリを覗き見]
3つ目は、複数のアプリが同時に装置を触って、出力が混ざって壊れることなんだ。 [画面: 困りごと③ 同時アクセスで出力が混ざる]
だからアプリには自分のメモリだけを触らせて、危ない操作は OS の本体、カーネルに閉じ込めているよ。 [画面: 上段＝アプリ（自分のメモリのみ）、下段＝カーネル（装置・全体管理）]
でも完全に閉じ込めたら、画面に1文字出すことすらできなくなっちゃうよね。
そこで「OS の決まった入口から安全にお願いする仕組み」、システムコールがあるんだ！ [画面: 境界線にある唯一の窓口「システムコール」]
動きをイメージするなら、「ガラスの仕切りがある役所の窓口」がわかりやすいよ。 [画面: ロビー（アプリ）と事務室（カーネル）を隔てる窓口]
ロビーのアプリは仕切りで止められて、奥の事務室へ勝手には入れないんだ。
頼みたいときは窓口のトレイに「手続き番号」と「必要な情報」を置いて呼び鈴を鳴らすよ。 [画面: トレイに「番号：16」と「出力先・文字・文字数」を置いて呼び鈴]
すると事務室のカーネルが中身を確かめて安全に作業し、結果をトレイで返してくれるんだ。
ただ、この窓口のたとえは、実際の RISC-V 版 xv6 と大きく違う点が3つあるんだ。 [画面: 窓口の比喩と実際の違い（3点）]
1つ目は、アプリとカーネルという2人の人間が向かい合っているわけではないことだよ。
たった1つの CPU コアが、帽子をかぶり直すみたいに権限を切り替えてカーネルを動かし始めるんだ。 [画面: 1つのCPUが帽子をかぶり直して事務室側へ回る]
2つ目は、トレイが紙ではなく、CPU 内部にある「レジスタ」という少数の置き場所だということだね。
レジスタは1組しかないから、カーネルが動く前にアプリの値をメモリへ退避する必要があるよ。 [画面: 1組のレジスタ → メモリの退避シートへ丸ごと保存]
3つ目は、ロビーから事務室がガラス越しに見えているわけではないことなんだ。
アプリごとに見えるメモリの地図、「ページテーブル」がカーネルと別物になっているよ。 [画面: アプリ用のメモリ地図（カーネル領域は記載なし・通行禁止）]
カーネルの番地は地図にないか通行禁止だから、触れた瞬間に CPU がエラーで止めるんだ。
それじゃあ、画面に文字を出す write で2文字書くときの実際の往復を追ってみよう！ [画面: システムコール往復の旅（ユーザーモード ⇄ スーパーバイザーモード）]
xv6 は制限付きの「ユーザーモード」と、特権付きの「スーパーバイザーモード」を切り替えて使うよ。
アプリが正当に特権モードのカーネルを呼ぶ手段は、専用命令の ecall だけなんだ。 [画面: 唯一の正当な入口「ecall 命令」]
write を呼ぶとき、アプリは a0 からのレジスタに出力先や文字数などの引数を最大6個入れるよ。
そして小さな入口で、a7 レジスタに write の番号 16 を入れて ecall を実行するんだ。 [画面: a0〜に引数、a7に番号16を入れて ecall]
ecall が実行されると、CPU は瞬時に特権のスーパーバイザーモードへ切り替わるよ。
同時に ecall 自身の番地と、割り込みなどと見分ける理由番号 8 を記録して受付番地へ飛ぶんだ。 [画面: ecallの4動作（①特権昇格 ②番地記録 ③理由8番 ④受付へジャンプ）]
ただ、CPU が自動でやるのはここまでで、メモリの地図もレジスタもまだアプリ用のままなんだ。
普通の場所で地図をカーネル用に変えたら、実行中の命令自身の番地が消えて暴走しちゃうよね。
そこで活躍するのが、メモリ1区画、つまり1ページ分の「トランポリン」という飛び込み台だよ！ [画面: 両方の地図の最高番地に共通配置された「トランポリン」]
ここだけは両方の地図で同じ一番上の番地にあるから、地図を切り替えても足場が消えないんだ。
トランポリンは、実行中のプログラム、つまりプロセスごとの退避シートにレジスタ一式を保存するよ。
そしてカーネル用の地図に切り替えて、C言語の usertrap 関数を呼び出すんだ。
usertrap は理由番号が 8 だと確かめると、戻り先の番地に 4 バイトを足して次へ進めておくよ。 [画面: usertrap で戻り先番地に +4 バイト → syscall へ]
続く司令塔の syscall 関数が、退避シートの a7 にある番号 16 から write の本体を動かすんだ。
無事に書けたら文字数の 2 を、未登録の番号ならマイナス1を、退避シートの a0 欄に書き込むよ。 [画面: 処理結果（2文字）を退避シートの a0 欄に格納]
さあ、いよいよ帰り道、お便りにあった usertrapret の答え合わせだよ！ [画面: お便り回収「usertrapret は今どうなった？」]
2019年版をもとにした日本語訳では、usertrap の最後で usertrapret を呼んでいたんだ。
そこからトランポリンの帰り道へ飛び込んでいたけど、今のコードと MIT 英語版では廃止されたよ。
代わりにまず prepare_return という関数で、ユーザーモードへ戻るための設定を整えるんだ。 [画面: prepare_return() で復帰設定 → usertrap が直接リターン]
そのあと usertrap 自身が、アプリ用のメモリ地図の設定値をリターンでそのまま返すんだ。
行きのトランポリンでは、usertrap を呼ぶ命令のすぐ次の行に帰り道の処理が並んでいるよ。
だから普通にリターンするだけで、トランポリンの帰り道へ直接戻って地図を受け取れるんだね！ [画面: トランポリンの呼び出し直後の行（帰り道）へ直接戻る]
最後はトランポリンで地図をアプリ用に戻してレジスタを復元し、a0 に結果の 2 を持って再開するよ。 [画面: a0 に戻り値 2 を持ってアプリの次の命令へ復帰]

syscall 関数で「処理関数を呼んだすぐ後ろ」に、名前と戻り値を出すコードを追加するんだ。
コマンドを受け付けるシェルで埋まらないよう、プロセス名が echo のときだけ表示するよ。
文字を出す echo に英語の挨拶である2文字の hi を渡して動かしてみるね。
echo は文字と改行で write を2回呼び、最後に終了の exit を呼ぶんだ。 [画面: echo の動作：write("hi") → write(改行) → exit(0)]
すると分身のプロセスを入れ替える exec と2回の write は出るのに、exit だけ出ないよ。 [画面: 実行ログ：exec と write は出るが exit がない]
バグじゃなくて仕組みどおりなんだけど、どうして exit だけ出ないのかな？
ヒントは「処理関数を呼んだすぐ後ろ」に置いたことだよ、ちょっと考えてみてね。

<!-- 間: 3秒 -->
<!-- SE: 正解チャイム -->
正解は、「exit に入るとプロセスが終了して、syscall 関数の次の行へ二度と戻らないから」だよ！ [画面: 正解②「exit は別プロセスへCPUを譲り戻ってこない」]
exit は別のプロセスへ CPU を譲ってしまうから、後ろに書いた表示コードには帰ってこないんだ。
私も最初に試したとき、「あれ、条件式を間違えたかな」って焦っちゃったお気に入りの問題だよ。
