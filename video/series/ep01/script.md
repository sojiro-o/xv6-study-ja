## 3. メイン前半：xv6ってどんなOS？ カーネルとシェルの意外な関係

<!-- SE: ページをめくる音 -->
まずは教科書の序文にある、xv6 の生まれ故郷の話から始めよう。 [画面: メイン前半「xv6の成り立ちとOSの3つの役割」]
xv6 は、1970年代に作られた古典の名作 OS、Unix の第6版である v6 が手本なんだ。
その設計を受け継ぎつつ、現代のマルチコアの RISC-V コンピュータ向けに C言語で書かれているよ。 [画面: 古典の名作 Unix v6 → C言語と RISC-V で再設計]
RISC-V というのは、CPU が直接理解できる命令の言葉の規格のことだね。
ちなみに日本語訳の序文では MIT の OS 講義の番号が 6.828 だけになっているよ。
最新の英語版では、現在の講義番号である 6.1810 も並んで紹介されているんだ。
この教科書には、「解説と一緒に本物のソースコードを全部読む」という伝統があるよ。 [画面: 解説書と本物のソースコードを並べて学ぶスタイル]
現代の Linux は何千万行もある巨大な山だけど、xv6 のカーネルは数千行ほどの小さな箱庭なんだ。
それなのに基本の仕組みは Linux や BSD や macOS、さらに Windows の一部とも通じているよ。
だから xv6 を知れば、普段使っている大きな OS の見取り図まで手に入るんだ！
じゃあ、そもそも OS ってコンピュータの中で何をする存在なんだろう？ [画面: 疑問「そもそもOSの仕事って何？」]
第1章の冒頭では、OS の役割を大きく3つにまとめているよ。
1つ目は、複雑な機械の違いを隠して、使いやすいサービスに整えることだね。 [画面: OSの仕事① ハードウェアの違いを隠す（抽象化）]
おかげでアプリは、ディスク装置の型番なんて気にせずにファイルを扱えるんだ。
2つ目は、1台のコンピュータを複数のプログラムで分け合って同時に動かすことだよ。 [画面: OSの仕事② 複数のプログラムで機械を分け合う]
3つ目は、プログラム同士が安全にデータを渡して協力する道を作ることなんだ。 [画面: OSの仕事③ プログラム同士が協力する道を作る]
そのサービスをアプリへ見せる接点のことを、インタフェースと呼ぶよ。
良いインタフェースを作る秘訣は、複雑な機能を詰め込みすぎないことなんだ。
「組み合わせやすい少数のシンプルな仕組み」に絞ることで、シンプルさと万能さを両立しているよ！ [画面: 少数のシンプルな部品 × 組み合わせ ＝ 大きな表現力]
ここで、これから毎回登場する大切な言葉を3つだけ覚えよう。
1つ目は「プロセス」、いま実行されている最中のプログラム1つひとつのことだよ。 [画面: 用語① プロセス ＝ 実行中のプログラム]
プロセスは自分のメモリに「命令」「変数のデータ」「スタック」の3つを持っているんだ。
スタックというのは、関数呼び出しの戻り先や一時変数を積んでおく作業机のことだね。
2つ目は「カーネル」、たくさんのプロセスにサービスを提供するただ1つの特別な管理プログラムだよ。 [画面: 用語② カーネル ＝ ただ1つの特別な管理プログラム]
普段、プロセスは制限付きの「ユーザー空間」で動き、CPU の保護機能で自分のメモリしか触れないんだ。
そして3つ目が、カーネルに仕事を頼む決まった窓口、「システムコール」だよ！ [画面: 用語③ システムコール ＝ カーネルを呼ぶ決まった窓口]
システムコールを呼ぶと、ハードウェアが権限を高めて特権付きの「カーネル空間」へ入るんだ。
カーネルが作業を終えて結果を返すと、プロセスはまたユーザー空間へ戻って続きを走るよ。
イメージするなら、「1つの厨房を守るシェフと、個室のお客さんたち」に似ているね。 [画面: 厨房のシェフ（カーネル）と個室のお客さん（プロセス）]
お客さんのプロセスは勝手に厨房の器具を触ったり、隣の個室を覗いたりはできないんだ。
用事があるときだけ、窓口に注文票を出してシェフのカーネルに頼むんだよ。
ただ、このレストランのたとえは、実際の xv6 と違う点が3つあるんだ。 [画面: レストランの比喩と実際の違い（3点）]
1つ目は、シェフとお客さんという別々の人間が向かい合っているわけではないことだよ。
同じ CPU が権限を切り替えて、アプリの続きとしてカーネルの命令を自分で動かすんだ。 [画面: 違い① 同じCPUが権限を切り替えて両方を動かす]
2つ目は、注文票に自由な文章で何でもお願いできるわけではないことだね。
今の xv6 が用意しているシステムコールは、あらかじめ決まった22種類だけなんだ。 [画面: 違い② 注文できる手続きは決まった22種類のみ]
3つ目は、個室の壁が木の扉ではなく、CPU のハードウェア保護機能で守られていることだよ。 [画面: 違い③ 個室の壁はCPUのハードウェア保護機構]
さあ、ここでお便りの2つ目の疑問、「シェルは何者なのか」を解き明かそう！
ここであなたに1つ目の予想タイムだよ。
もしシェルがカーネルの一部ではなく、ただの普通のアプリだとしたら、どんな良いことがあると思う？ [画面: 予想してみよう①「シェルが普通のアプリだと何が嬉しい？」]
少し間を置くから、使う人の気持ちで想像してみてね。
<!-- 間: 2秒 -->
実はね、シェルはカーネルの一部ではなく、ユーザー空間で動く「ただの普通のプログラム」なんだ！ [画面: 正解：シェル（sh）はカーネルの外にある普通のユーザープログラム]
xv6 でも一般アプリと同じ場所に sh という名前で置かれていて、特別な特権は何も持っていないよ。
だからこそ、カーネルを書き換えなくても、好みに合わせていろんなシェルへ自由に取り替えられるんだ！
しかも普通のアプリとしてシェルを作れること自体が、システムコールの設計が優秀な証拠なんだね。

## 5. メイン後半：分身するfork、変身するexec、見守るwait

<!-- SE: ページをめくる音 -->
それじゃあ後半戦、シェルがどうやって別のコマンドを動かしているのか、核心へ踏み込もう！ [画面: メイン後半「プロセスを生み出し入れ替える仕組み」]
ここからは教科書の1.1節、「プロセスとメモリ」の内容だよ。
カーネルは複数のプロセスに CPU を順番に貸し出して、同時に動いているように見せるんだ。
これを「タイムシェア」、つまり時間の分かち合いと呼ぶよ。
休むプロセスについては、CPU の中にある小さな手元メモ、つまりレジスタをカーネルが保存しておくんだ。
そして次にそのプロセスの番が来たら、保存したレジスタを元に戻して続きから再開するよ。
また各プロセスには、見分けるための背番号である「PID」が付けられているんだ。 [画面: 各プロセスに付けられる背番号「PID」]
では、あるプロセスが新しいプロセスを生み出したいときは何を呼ぶんだろう？
最初の主役が、fork というシステムコールだよ！ [画面: 主役① fork（プロセスを複製するシステムコール）]
fork は英語で「二股に分かれる」という意味なんだけど、動きも本当にユニークなんだ。
あるプロセスが fork を呼ぶと、その瞬間のメモリを丸ごとコピーした新しいプロセスが作られるよ。
命令もデータもスタックもそっくり同じで、元の方を「親プロセス」、新しい方を「子プロセス」と呼ぶんだ。 [画面: 親プロセスからメモリ丸ごとコピーで子プロセスが誕生]
一番驚くのは、fork を呼んだのは1回なのに、「親と子の両方で結果が返ってくる」ことだよ！
でも中身がそっくり同じだったら、自分が親なのか子なのか区別がつかないよね？
そこで fork は、親には「生まれた子の PID」、子には「0」を戻り値として返すんだ！ [画面: forkの戻り値：親には「子のPID（正の数）」、子には「0」]
だから戻り値が 0 より大きければ親の処理、0 なら子の処理、と綺麗に書き分けられるんだよ。
もしメモリ不足などで作れなかったときだけ、親にマイナスの 1 が返るよ。
教科書の最初の例でも、親と子がこの戻り値で役割を分けているんだ。
親は子の PID を printf で出してから、wait というシステムコールを呼んで子の終了を待つよ。 [画面: wait ＝ 子の終了を待ち、終了した子のPIDを受け取る]
一方、0 を受け取った子はメッセージを出してから、exit を呼んで自分自身を終了させるんだ。 [画面: exit ＝ 自身の実行を終え、メモリ等の資源を解放する]
exit には慣習として成功なら 0、失敗なら 1 を渡し、親は wait でその番号を受け取れるよ。
親が終了番号を気にしないときは、wait の受け取り先の番地に 0 を渡せば省略できるんだ。
もし子が1人もいないのに wait を呼んだら、待たずにすぐマイナスの 1 が返る仕組みだね。
さあ、ここであなたに2つ目の予想タイムだよ！
親が出す「子が生まれたよ」という表示と、子が出す「終了するよ」という表示、必ず親が先に出るかな？ [画面: 予想してみよう②「親の表示と子の表示、必ず親が先に出る？」]
それとも子が先に出ることもあるかな、ちょっと予想してみてね。
<!-- 間: 2秒 -->
正解は、「どちらが先に出るかは決まっていなくて、逆になることも混ざることもある」だよ！ [画面: 正解：CPUの割り当て次第で親子の出力順は入れ替わる]
親と子は独立して走る別々のプロセスだから、どちらが先に printf へ届くかはタイミング次第なんだ。
ただ、親が wait の後ろに書いた完了メッセージだけは、子が exit したあとに必ず最後に出るよ。
また、マンガの分身と違って、生まれた瞬間から親と子のメモリもレジスタも完全に別物なんだ。
だから親が自分の変数を書き換えても、子プロセスの変数は 0 のままで一切影響を受けないよ。
さて、fork で分身は作れたけれど、それだけだと親と同じプログラムしか動かせないよね。
シェルから文字を出す echo のような別のプログラムを動かすために、2人目の主役 exec が登場するよ！ [画面: 主役② exec（メモリを別プログラムに入れ替える）]
exec は、ディスク上の実行ファイルを読み込んで、今のプロセスのメモリを丸ごと新しい中身に上書きするんだ。
xv6 の実行ファイルは ELF という形式で、どこが命令でどこから実行を始めるかが記録されているよ。
exec には「実行ファイル名」と「文字列の引数リスト」の2つを渡すんだ。
たとえば echo に英語の挨拶である hello を渡すなら、プログラム名の echo と hello を並べて渡すよ。
ここで「変身」というイメージと実際の動きで気をつけたいポイントが1つあるんだ。
exec は新しいプロセスを増やすのではなく、同じプロセスのままメモリの中身だけを入れ替えるんだ。 [画面: execの要点：プロセス自体は増えず、メモリを上書きして最初から実行]
そして成功したら元のプログラムには二度と戻らず、新しいプログラムの最初から走り始めるよ！
元の場所へ戻ってくるのは、指定したファイルが無いなどのエラーで失敗したときだけなんだ。
これでついに、シェルである sh が echo hello を動かす手順が全部つながるよ！ [画面: シェル（sh）が echo hello を動かす4ステップ]
まず親の sh は、あなたがキーボードから打った1行を読み取るんだ。
次に fork を呼んで、シェル自身の分身である子プロセスを作るよ。
親の sh はそのまま wait を呼んで、子が終わるまで静かに待っているんだ。
一方、子の sh は exec を呼んで、自分自身のメモリを echo プログラムに丸ごと入れ替えるよ！
入れ替わった echo が hello と画面に出して exit すると、待っていた親の sh が目を覚ますんだ。
そしてまた次のコマンド入力を待ってくれる、という美しい連携なんだね！
ここで最後の3つ目の予想タイムだよ！
せっかく fork でメモリを全部コピーしたのに、すぐ exec で捨てて上書きするなんて無駄に見えるよね？ [画面: 予想してみよう③「なぜ fork と exec を1つに合体させないの？」]
どうして最初から1つのシステムコールに合体させなかったのか、ちょっと想像してみてね。
<!-- 間: 2秒 -->
実はね、「fork してから exec するまでの短い隙間」に、子プロセス側だけで大事な準備ができるからなんだ！ [画面: 理由：fork と exec の「隙間」で子だけの出力先を差し替えられる！]
